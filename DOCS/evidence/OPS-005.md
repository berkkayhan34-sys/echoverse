# OPS-005 — temporary MacBook self-hosted deployment

- Status: in progress; host re-deploy pending after localhost bind hardening
- Decision: [`ADR-0024`](../decisions/0024-macbook-self-hosted-deployment.md)
- Runbook: [`macbook-server.md`](../macbook-server.md)

## Completed in the repository

- Added the self-hosted workflow at
  `.github/workflows/deploy-self-hosted.yml`.
- Added the non-root user systemd unit at
  `deploy/systemd/echoverse.service`.
- Fixed the intended service port at `3001` and documented Cloudflare origin
  mapping to `http://localhost:3001`.
- Kept runner registration tokens, PostgreSQL credentials, JWT secrets, and
  founder identity out of Git.

## Host evidence collected so far

- AnySCP is connected to `echoverse-server` (`192.168.111.42`).
- The GitHub runner service is `active (running)` and GitHub reports one
  available repository runner with the `echoverse-server` label.
- PostgreSQL is installed on the host and the user-owned
  `~/.config/echoverse/server.env` is readable only by `berkkayhan` (`0600`).
- `echoverse.service` is `active (running)` and `enabled`; the host-local
  `/health` endpoint returned `ok: true` for server version `1.9.9`.
- The configured PostgreSQL connection authenticated as `echoverse` against
  the `echoverse` database.
- A custom-format backup was created at
  `~/.cache/echoverse/ops-005-20260831204926.dump`.
- A second custom-format backup was created at
  `~/.cache/echoverse/ops-005-20260831210731.dump` and restored successfully
  into the temporary database `echoverse_ops005_20260831210731` using
  `pg_restore --dbname=...`; the restored database contained `17` application
  tables. The temporary database was then dropped with `dropdb`.
- From the Windows development host, the Cloudflare hostname
  `echoverse.borayarkin.net` resolved to Cloudflare addresses and accepted
  HTTPS. `GET /health` returned HTTP `200` with `ok: true`, server version
  `1.9.9`, protocol version `2`, and database `postgres`. `GET /` returned
  HTTP `200` with the EchoVerse web application HTML and its bundled assets.
  These requests were read-only and made no host or production-data changes.
- A controlled `systemctl --user restart echoverse` was issued through AnySCP;
  the terminal returned to a normal prompt without an error. A follow-up
  Cloudflare `GET /health` from the Windows host returned HTTP `200` with
  `ok: true` and version `1.9.9`, confirming that the service recovered after
  the restart.
- After a controlled host reboot, AnySCP reconnected and `who -b` reported
  system boot at `2026-08-31 21:29`. The post-boot systemd status showed
  `echoverse.service` `active (running)` and `enabled`, with the server
  listening on port `3001`. The process list also showed the GitHub runner
  listener and `cloudflared` tunnel running after boot. A post-boot Cloudflare
  `GET /health` returned HTTP `200` with `ok: true` and version `1.9.9`.
- `sleep.target`, `suspend.target`, `hibernate.target`, and
  `hybrid-sleep.target` are all `masked` and `inactive (dead)`, preventing
  the temporary host from entering those power states through systemd.
- A post-reboot `ss -ltnp` check showed the pre-hardening EchoVerse process
  listening on `0.0.0.0:3001`; this matched the then-current ADR-0024 binding.
  The binding decision has since been changed to `127.0.0.1` in the service
  configuration and server code. The host must be re-deployed and rechecked
  before this item can be marked complete.
- Repository verification for the bind hardening passed: the focused config
  and server tests passed (`11` tests), workspace typecheck passed, and the
  workspace build passed. The test suite also rejects malformed `HOST` values
  and accepts `127.0.0.1`/`localhost` explicitly.

## Pending host evidence

The localhost-only bind hardening is implemented in the repository but has not
yet been deployed to the host. The first restore attempt was blocked because
the application role
cannot create a database; the follow-up used the PostgreSQL administrator only
to create/drop the temporary test database. No production database writes were
made. This record must remain incomplete until the remaining checks are
captured from the host.
